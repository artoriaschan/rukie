# 文件变更基线表示模型已知内容，与提醒在同一事务中推进

## 问题

用户或子代理可能在模型读取后修改文件。仅依赖修改时间不足以避免覆盖；先更新基线再发送提醒，则可能把模型从未获知的变化误记为已知。

## 决定

read、write、edit 维护各 Session 独立的文件跟踪集。即使 read 只返回片段，基线也描述整个文件。请求前用元数据筛选变化，write、edit 前用内容 hash 检查陈旧状态；glob、grep、bash 不建立这种已读基线。

基线表示模型已经获知的内容。可交付的变更 reminder 与对应基线更新或删除，在同一次原生存储事务中提交；提交前保留旧基线和保守的 stale 标记。事务失败保留可重试的变化，撤销未落盘的内存提醒，不把未送达的内容算作模型已知。

reminder 受请求预算约束，延期的变化不推进基线。无法提供旧内容的二进制、大文件或 Resume 场景只报告路径，并保持 stale，直到重新读取。Tool State 保存路径、元数据、hash 与重读标记，不持久化完整文件内容。

Compaction 保留当前进程的跟踪内容；对话 Rewind 按分支状态恢复，只复用 hash 一致的内存内容。只恢复代码时，下次请求把变化报告给保留的对话。子 Session 独立跟踪，子代理写入由父级作为外部变化检测。

依据：[文件变更检测规格](../../.scratch/file-change-detection/spec.md)。能力边界由 [ADR-0011](0011-agent-module-ownership.md)与[当前架构](../architecture.md)说明。

## 备选方案

- 使用文件 watcher 或仅比较时间戳：增加后台监听生命周期，也不能替代写入前的内容一致性检查；规格选择请求前检测与 hash 守卫。
- 把完整文件内容持久化进 Tool State：增加存储和敏感内容留存；规格选择元数据恢复并要求重读。
- 提前推进基线：提醒预算不足或保存失败时，会丢失模型尚未知晓的变化。

## 影响

写入路径和提醒持久化必须协作，不能各自独立提交基线。Resume 后的路径提醒比当前进程内的 diff 更保守；跟踪守卫保护已跟踪文件，不覆盖任意 shell 或 MCP 副作用。
